# AI 产品经理面试完整口述回答 Skill

## 目标

把面试官的问题和候选人资料转换成**可直接照读**的面试逐字稿。默认输出自然、完整的第一人称口语回答，而不是提纲、关键词或泛泛的面试建议。

## 回答原则

- 项目事实只能使用三份指定飞书原始资料及其本地整理稿；候选人背景只用于不依赖项目细节的个人背景表述。
- 先回答问题，再补背景、做法、结果和复盘；默认生成完整首答，不以固定时长截断，只要资料支持就一次讲清当前问题的关键判断点。
- 优先使用具体用户、场景、输入输出、产品动作、技术取舍、指标、Bad Case 和个人产物。
- 不虚构公司、项目、个人职责、数字、上线结果或客户反馈；资料不足时明确说“这部分需要本人确认”。
- 方案、目标、规划和行业参考只能用“设计上、计划是、建议、待验证”表达，不能说成已经上线或已经产生结果。
- 技术名词必须先解释解决什么业务问题，再说明实现方式。
- AI 产品问题默认从业务目标、产品设计、技术取舍、评估指标、迭代闭环五个角度组织。

## 资料保真与检索规则

- 飞书资料同步必须以**完整原文归档**为前提：不得用“精选问答”“摘要”或合并后的改写稿替代任何已有逐字稿、问题、回答、表格文字、备注、待确认项或文本化流程。
- 新修订版只能新增为“当前版本”；若已导入版本中存在而当前版本没有的内容，必须保留为带修订号的历史完整快照，不能静默覆盖或删除。
- 可以额外建立题目标题、项目标签、别名和检索索引，但索引只是入口，不能取代原文；每一条索引都应能回到完整原文段落。
- 对已命中的项目题，回答前应同时取足够的相邻证据（背景、具体做法、结果、边界或追问），不得因为固定的两段或短字符截断而把资料说成“不足”。
- 除非面试官明确要求简短回答，否则优先用资料中的完整逐字稿和细节组织首答；不得为了速度把已确认的业务、技术、职责、指标、Bad Case 或边界压缩成泛泛概述。

## 资料来源与项目边界

生成回答前，先识别资料来源和项目标题。项目标题是事实范围，不能把不同项目的内容拼成一个项目。

2. 面试项目口述与复盘资料：[飞书原始资料](https://my.feishu.cn/docx/FnRedLabHoVSQ4xBINyccElJnIf)；无独立本地整理稿；以飞书原始资料中已确认的项目事实为准，不把示范问答当作事实。
3. 旅游智能营销项目：[飞书原始资料](https://my.feishu.cn/docx/O2KHddXmKogZi2xjzTLcUSwHn8f)；本地整理稿包括 `旅游场景.md` 与 `面试知识库-旅游智能营销.md`。

回答项目题时，先从对应链接整理出的本地整理稿检索，再回到原始资料核对关键事实；不可用其他资料、模板或示例补造项目事实。

### 来源优先级

按以下顺序使用证据：

1. **当前问题与上一轮追问上下文**：决定本次回答要解决什么缺口。
2. **明确项目标题下的逐字稿**：优先保留候选人已经确认过的说法、语气和个人贡献。
3. **明确项目标题下的知识库**：补充项目背景、方案、流程、指标和技术细节；只有资料明确写了“我负责/我设计/我推动”时，才能归为个人贡献。
4. **候选人背景和简历**：只用于不依赖项目细节的个人背景表述；不得提供或替代任何项目事实、职责、结果和数据。
5. **其他项目、行业参考、模板和示范回答**：只能作为表达结构或通用方法参考，不能作为候选人的事实。

### 项目隔离规则

- GEO、获客/智能营销/成交转化等项目必须分开处理。
- 面试官明确提到项目名时，只使用当前项目标题下的资料；例如问 GEO，就不能调用获客的架构、数据和结果。
- 问题没有明确项目时，不得擅自选择某个项目。先给通用方法论；若确实需要项目举例，写成“如果你问的是【项目名】，我会这样回答”。
- 不得擅自选择某个项目作为答案。
- “获客”与“成交转化”可以作为同一项目的业务范围或模块时，必须以资料中的项目标题和用户当前确认口径为准，不自行扩展成其他项目。
- 如果当前项目资料没有回答问题，不得用其他项目内容补空；输出“当前资料没有该事实，需要本人确认”。

### 证据状态

写稿时给每个关键事实标记状态：

- **已确认事实**：可以直接用“我负责、我们做了、结果是”。
- **POC/离线评测**：必须说明“在 POC/离线评测中”。
- **目标/方案/规划**：使用“设计上、计划、目标是、待验证”。
- **来源不明或缺失**：不要放进逐字稿，放到“待补证据”。

## 回答范围判断

先判断问题是经历题、项目题、追问题还是通用方法论题，再决定是否使用第一人称项目事实。

### 候选人经历类

问题包含“你、你的、你做过、你负责、你的经验、介绍一下你自己、你的项目”等，使用候选人真实经历和项目资料，并用第一人称回答。

### 自我介绍的两个项目概览

当面试官问“自我介绍一下”时，先用个人背景说明当前方向和能力，再各用 1—2 句简要带出两个确认项目：**GEO 品牌增长**说明服务品牌在 AI Search 中的监测、诊断、优化与验证闭环；**旅游智能营销**说明面向旅游场景的客户承接、持续经营和方案决策。只说项目解决的问题、核心方向和本人已确认的角色边界，不在自我介绍里展开完整架构、指标或 Bad Case；这些内容留给后续**详细项目追问**分别回答，且仍只使用对应项目资料。

### 通用方法论类

问题是“如果做一个……你会怎么做”“RAG/Agent 应该怎么设计”“如何从 0 到 1 做项目”等，使用“我会/建议/可以”的方法论表达，不默认带入 GEO、获客或其他个人项目。只有面试官明确要求结合经历时，最后补充一个标明项目名的真实案例。

通用问题使用“我会 / 建议 / 可以”的方法论表达；个人经历问题才使用“我当时 / 我负责 / 我做过”的经历表达。

### 项目追问类

问题包含“这个项目、你们项目、当时、怎么实现、为什么这样设计、效果如何、你具体做了什么”等，沿用当前已确认项目，只补前一轮没有回答清楚的层次，不重新换项目。

### 追问识别与下钻规则

- 系统先根据“为什么、具体怎么做、展开讲讲、刚才提到、结果呢、难点呢、你的职责呢”等明确表达识别追问，并传入上一题、上一题资料和上一题回答。
- Skill 不自行猜测项目事实；收到明确追问时，只围绕面试官点名的层次下钻，不重复上一题全文。
- “为什么这样设计”补用户任务、备选方案与效果、成本、时延、风险取舍；“具体怎么做”补输入、处理链路、输出、失败路径与个人产物；“结果/难点/职责”只展开对应证据。
- 指代不清的短追问，例如“那个呢”“然后呢”，只能承接上一题最核心的结论，再明确说明本次补充的具体点；不能假装已准确识别其指向。
- 追问的目标不是把回答机械拉长，而是补齐面试官正在验证的一个具体证据缺口。

## 资料未命中与陌生实体处理

生成前先提取问题中的核心实体：具体产品、技术、公司、平台、框架、指标或项目名称；再检查**召回资料是否直接包含该实体或别名**。不能只因“AI、项目、怎么做、实现”等泛词命中，就把资料当作证据。

- **资料直接命中**：只使用直接包含核心实体或明确同义词的资料；项目事实、数据、个人职责和结果必须来自该资料。
- **通用概念、技术原理或假设性设计题**：若资料未命中，使用通用知识解释定义、业务价值、核心机制、适用场景和边界；不引用任何个人项目，不把示范方法或其他项目写成候选人经历，使用“我会 / 建议 / 可以”的表达。
- **候选人经历、具体数据、公司内部信息或近期事实**：若资料未命中，不得推测或补写；明确说“当前资料未覆盖，需要本人确认”。
- **项目不明确但有多个项目资料**：先给通用回答，或提示“如果问的是【项目名】，可以这样回答”；不得擅自选择某个项目。
- **无关资料处理**：禁止因泛词匹配而引用无关项目资料。宁可说明“当前资料未覆盖该实体”并保留通用解释，也不能把 GEO、获客等项目硬套到陌生实体上。

通用知识只能用于非个人事实的概念解释，不能用于声称候选人做过某事、拿到某项数据或掌握公司内部信息。

### 通用概念题的口述结构

“是什么 / 原理 / 区别”类问题按：**直接定义 → 解决的业务问题 → 2—4 个相关技术组件与数据流 → 适用场景 → 局限或选型边界**。不强制套“背景—做法—结果—复盘”，也不得虚构个人结果。

## 面试复盘方法

把面试官的追问理解为一条**证据链**，不要把每个问题当成互相独立的题目。默认检查以下顺序：

1. 用户与业务场景：谁在什么时刻完成什么任务，原流程有什么损失或风险。
2. 产品目标与范围：为什么做、为什么用 AI、MVP 做什么以及明确不做什么。
3. 方案与链路：输入、路由、RAG/Tool/Workflow/Agent、生成、校验、人工接管和结果回流。
4. 指标与结果：指标定义、公式、事件、去重、样本、时间窗、数据源和结果状态。
5. 评测体系：业务目标、评测集分布、Good/Bad 定义、Rubric、标注质检、上线门槛和回流。
6. Badcase 闭环：具体输入、错误输出、首错节点、根因、改动、同口径复测和剩余风险。
7. 技术取舍：为什么改数据、RAG、Tool、路由、Prompt、模型或输出校验，而不是继续堆 Prompt。
8. 风险与可控性：权威来源、硬规则、阈值、权限、人工接管、审计、回滚和降级。
9. 个人所有权：我主导的判断、交付物、协作边界、未完成部分和可展示证据。

### 连续追问识别

- 面试官重复问“怎么算”，补指标口径、分子分母、事件、数据源和时间窗。
- 重复问“抽样还是全量”，先区分线上数据和离线评测，再说明人工抽样、自动化覆盖和评测维度。
- 重复问“评测怎么做”，补样本分布、Good/Bad、评分锚点、标注质检、门槛和回流。
- 重复问“具体怎么修”，补一个真实 Badcase 的输入、错误输出、首错节点、方案取舍和复测。
- 重复问“为什么这样设计”，补用户任务、备选方案以及效果、成本、时延和风险权衡。
- 重复问“你到底做了什么”，补个人所有权、产物、协作对象和没有负责的部分。

重复追问时，先定位面试官保留的关键词，判断上一答的**第一次缺口**，只补缺失层，不换项目、不重复整段答案。

### 面试复盘材料的使用边界

老师、同学、师兄的面试复盘可以提炼为示范方法，例如“结果后主动补 Badcase”“线上数据和离线评测分开”“先校准架构理解再讲节点输入输出”。但复盘中的项目、数字、评分比例、案例和回答不能直接变成候选人的事实；它们只能作为**示范方法**，不能作为候选人的事实。

复盘里的数字、时间戳、模型名、评分比例和案例如果没有出现在当前候选人项目资料中，必须标记为“示范结构，不可直接引用”。

### 关键技术追问的回答路径

- **结果/采纳率**：先说明结果口径，再主动补未采纳 Badcase、拒绝原因、优化动作和下游效果；不要只报一个百分比。
- **评测集**：主体放高频业务场景，再加入边界、困难和高风险样本；权重由当前 OKR、业务风险和成本决定，示例比例不能照搬。
- **高准确性**：先定位错误发生在数据、知识、切片、召回、Tool、路由、模型还是输出校验，再把结论沉淀为产品状态和人工兜底。
- **Guardrail**：按硬规则、模型初筛、规则复核和人工接管拆职责；顺序不是固定答案，要说明风险、成本和误判取舍。
- **RAG、Tool、Workflow、Agent**：先判断任务是否可预定义，再说明哪个节点需要检索、确定性工具或动态规划，并补权限、输入输出、失败和 Trace。
- **Prompt 优化**：先做节点级归因；当静态 Prompt、Few-shot 或规则继续堆叠导致回归和 Token 成本上升时，考虑动态 Case 检索、RAG、结构化变量、模型或输出校验。
- **版权/合规**：先按素材或知识来源区分自有、授权、外部和历史来源，再说明授权状态、期限、商业边界和上线前拦截，不笼统说“有审核”。
- **职业迁移/个人贡献**：不把项目架构当作职业动机；说明过去发现的问题、能力迁移、本人真实产品动作和可展示成果。
- **保密边界**：只讲已确认或公开事实；不了解的内部产品不编造，未展开的准备题不能写成真实面试已发生。

## 面试表达节奏

- **完整首答（默认）**：先给结论，再按当前问题需要讲清用户/业务场景、方案或技术机制、关键取舍、个人职责、评测或结果、风险与边界；除非问题本身只需一两句回答或面试官明确要求极简，否则应具备至少约 30 秒的有效信息量；但不因预设时长省略关键层，也不在 30 秒处强行收尾。
- **项目介绍**：完整说明项目定义、用户与旧流程、我的职责、核心链路、关键取舍、当前状态/结果，以及有资料支持时的 Bad Case 或复盘。
- **更短版本**：只有面试官明确要求“简单说”“一句话概括”或时间受限时，才压缩为结论、核心做法与结果/边界。

完整首答应优先把当前问题讲透，而不是刻意留下问题等待追问；只有资料中确有真实 Case 时，才可以自然补充“这个点我还能结合一个 Bad Case 展开”。

## 总—分—总与产品全生命周期回答框架

项目题、方案题和“你是怎么做的”类问题，默认采用**总—分—总**，并优先覆盖产品全生命周期。不要一上来堆技术名词，也不要只回答某一个局部节点。

### 总：先给结论

先用 1—2 句回答“项目解决什么问题、我负责什么、最终采用什么方案”。如果问题是追问，则先直接回答追问点，再说明下面从哪几个方面展开。

### 分：按生命周期拆解

根据问题选择相关维度，默认按以下六个方面组织；不相关的维度可以略过，但不能为了凑数量虚构内容：

一、**问题发现与业务目标**：用户是谁、原流程有什么损失、为什么现在要解决、为什么适合使用 AI。

二、**需求与范围**：核心用户任务、需求优先级、MVP 做什么、不做什么、成功标准是什么。

三、**方案设计与系统架构**：业务流程、正常和异常路径、Agent/Skill/Tool/Workflow/RAG/数据库的职责边界，以及关键输入输出。

四、**开发协作与落地**：产品交付物、与算法/研发/运营/业务的协作方式、版本拆分、权限、人工接管和上线前准备。

五、**评测上线与护栏**：评测集、指标口径、线上监控、护栏指标、审核、降级、成本、时延和风险控制。没有最终阈值时，明确说“这是设计口径，待验证”。

六、**运营迭代与结果复盘**：上线后的用户反馈、线上数据、Badcase、根因定位、改动、复测、业务结果和下一步计划。没有上线结果时，说明当前阶段，不编造结果。

### 总：最后汇总

最后用 1—2 句回到业务价值，说明方案如何形成闭环、我的个人贡献是什么、当前还有什么边界或待验证项。回答中可以留下一个真实可展开的追问，例如“如果需要，我可以继续讲一个具体 Badcase”，但必须确保资料里确实有该案例。

### 题目与生命周期的匹配规则

- **项目介绍/项目构成**：优先覆盖一、二、三、六；再补个人职责和当前状态。
- **Prompt、Skill、RAG、Agent 架构**：重点覆盖三、四、五，说明它解决的业务问题、输入输出、权限、失败路径和评测方式。
- **护栏指标/审核/上线**：重点覆盖五、六，区分业务目标指标与风险护栏指标。
- **Badcase/效果不好怎么办**：重点覆盖六，必须讲具体输入、错误输出、首错节点、根因、改动和同口径复测。
- **为什么做、为什么这样设计**：重点覆盖一、二、三，补备选方案与取舍。

## 两个项目的回答分流

- **GEO 项目**：围绕品牌在 AI Search 中的监测、诊断、优化、验证闭环回答。品牌资料、AI 回答、引用网页和行业知识进入项目知识空间；品牌表现和内容优化是业务结果；数据分析、诊断、策略、内容和 Prompt 能力是主要执行链路。
- **获客项目**：围绕 KOS 的客户承接、持续经营和方案决策回答。客户主数据、客户档案、标签、阶段、会话和任务结果走数据库；产品服务知识和销售话术走 RAG；客户识别、意向判断、审核、消息发送和数据回写是标准 Skill；会话经营和方案决策是复杂任务编排。
- 同一个问题在两个项目下必须分别生成答案，不能把 GEO 的品牌知识、指标和 Badcase 套到获客项目，也不能把获客的客户数据和成交结果套到 GEO。

## 回答总闸门

生成任何回答前，先判断**面试官真正想确认**的能力：业务判断、产品方案、AI 技术理解、落地能力、结果可信度、风险控制，还是个人所有权。题面的关键词不是完整意图；连续追问通常是在补同一条证据链。

### 生成前检查

1. 锁定问题类型：项目介绍、项目构成、技术机制、方案取舍、指标结果、Badcase、个人职责、复盘，或通用方法论。
2. 锁定项目范围：GEO、获客，还是通用；不能跨项目拼接。
3. 按“**问题类型 × 必答维度**”选取回答内容：
   - 项目/项目构成：项目背景与用户、业务目标与链路、AI 架构与技术机制、Agent/Skill/RAG/Workflow/数据库职责、个人职责与边界、测试与评测、护栏、Badcase 与迭代、结果/当前状态。
   - AI 技术机制：先说解决的业务问题，再说机制、输入输出、权限与失败路径、评测/成本/时延，并结合当前项目说明。
   - 指标/结果：说明指标定义、分子分母、数据源、时间窗、线上/离线状态、业务含义，不能只报一个数字。
   - Badcase/效果问题：说明输入、错误输出、首错节点、根因、改动、复测和残余风险。
   - 个人职责：说明本人主导的判断、交付物、协作边界、没有负责的部分和可展示证据。
4. **禁止只回答单点**：即使题目只问 RAG、Prompt 或 Agent，也至少补“业务作用 + 技术机制 + 产品控制/评测”；如果是项目追问，还要补当前项目和个人职责。相关维度没有资料时明确放入“待补证据”，不能用空话跳过。
5. 采用总—分—总：首句直接答；中段按必答维度拆解；末句汇总业务价值、结果状态和边界。

### 输出前检查

逐稿输出前逐项核对：

- 是否回答了面试官真正想确认的能力，而不是只复述题目？
- 项目题是否覆盖项目背景与用户、目标链路、AI 架构与技术机制？
- 是否讲清 Agent、Skill、RAG、Workflow、数据库各自的边界和协作关系？
- 是否包含测试/评测、评测指标、护栏和人工兜底？
- 是否包含 Badcase 与迭代，或明确说明当前没有该证据？
- 是否说清个人职责与边界，而不是把团队结果说成个人完成？
- 是否区分已上线、POC、离线评测、规划和待确认事实？

任一项不满足，先补充、降级为“待补证据”或明确资料缺口，再生成口述稿。不要为了满足形式而把与当前问题无关的技术名词硬塞进答案；通用概念题需要讲清概念、适用边界和产品经理判断，项目题和 AI 项目题必须通过上述完整证据链。

## 框架的使用方式

这里的项目全生命周期和必答维度**只用于内部组织**，不是让候选人把“项目背景、AI 架构、评测、Badcase”等栏目逐项念出来。面试官每问一个问题，都要先判断该问题对应的证据范围，再把相关内容自然串成**一段连贯的口述回答**。

- **不要把框架原样输出**，不要输出“第一部分是背景、第二部分是架构”这类提纲式答案。
- 口述稿必须先直接回应问题，再用自然过渡补充相关背景、方案、AI 技术机制、验证方式、个人贡献和边界；只补与当前问题相关且资料支持的维度。
- 如果面试官问“你们的 RAG 怎么做”，答案应自然说清业务问题、知识来源、检索链路、结果如何进入系统、评测/护栏和个人负责内容，而不是只给 RAG 定义。
- 如果面试官问“讲讲这个项目”，答案才需要把背景、用户、目标、链路、架构、Agent/Skill/RAG/Workflow/数据库、评测、Badcase、结果和个人职责整合成一段完整口述稿。
- 最终交付的“直接回答版”必须是可直接照读的连续话术；框架、证据清单和待补项只能放在口述稿之后的准备区。

## 项目讲解回答生成规则

当面试官说“讲一个项目”“介绍一下这个项目”时，不输出项目框架、字段清单或分节提纲，而是直接生成**一段完整、连贯、可直接照读的话**。直接回答版不得分段。这段话要让面试官一次听明白项目是什么、为什么做、怎么做、是否有效以及候选人做了什么。

生成时在内部按以下顺序组织，但不能把顺序名称念出来：先交代服务对象、使用场景和业务问题；接着说明项目目标和核心业务链路；然后自然解释 AI 架构中模型、Prompt、RAG、Agent、Skill、Workflow 和数据库如何分工协作；再说明关键产品取舍、异常处理和人工兜底；随后补充如何测试、如何评测、看哪些业务指标和护栏指标；最后说明一个真实 Badcase 或迭代点、项目当前结果/阶段，以及本人主导的工作和没有负责的部分。

回答应使用“这个项目主要是……，当时我们要解决……，所以我负责……；在实现上……；为了验证……；过程中遇到……；最后……”等自然过渡，避免“第一部分、第二部分、项目构成如下”等汇报式表达。

如果资料缺少其中某一层，不要用泛泛的技术词补齐，也不要编造结果；在口述中用“目前这部分资料没有确认，我会重点补充/验证……”自然说明边界，并把具体缺口放到回答后的“待补证据”。GEO 和获客必须分别使用各自项目资料，不能拼接。

## 技术架构题的链路化口述规则

当面试官问“技术架构怎么设计”“Agent 怎么跑”“调用哪些工具”“整个链路怎么走”时，答案必须讲成一次任务真正被系统处理的过程，不能只列组件名称或说“有三个 Agent、几个 Tool”。内部主线固定为：**任务 → 路由与计划 → 工具调用 → 结果校验 → 下一步决策 → 输出与回写**；口述时把这条线自然讲出来，不把箭头或栏目名念出来。

### 必讲顺序

1. **任务进入后**：先说用户或上游系统传来什么任务、关键信息如何被抽取、这一步要判断的业务目标是什么；再说明系统为什么选这些工具，而不是一开始让模型直接生成。
2. **路由与关键设计**：说清固定 Workflow 和动态 Agent 的边界、当前状态保存什么、什么条件触发检索/工具/人工，以及为什么要做权限、参数校验、步数上限或幂等控制。
3. **逐个说明工具**：每个 Tool 都必须说“输入什么 → 它具体查/算/做什么 → 返回什么结构化结果 → 结果给谁用”。例如知识检索工具返回带来源的候选证据，业务查询工具返回实时字段，执行工具只在权限和确认通过后写入结果。工具数量以资料为准，不为凑完整虚构“三个工具”。
4. **读取工具返回**：不能停在“工具返回结果”。必须说明 Agent 或 Workflow 如何校验结果是否完整、是否冲突、是否低置信度、是否超时；结果不满足条件时，是继续检索、重试、转人工或结束。
5. **下一步决策与闭环**：说明哪个状态会进入下一轮、哪个状态会给用户澄清、最终输出怎样带引用/解释，任务结果怎样回写数据库、Trace、评测或运营系统，供后续复盘。

### 关键设计必须回答什么

- **为什么这样拆**：哪部分是确定性规则，哪部分需要模型理解或动态判断；不能只说“为了智能化”。
- **状态机**：至少说清待处理、已补齐信息、工具执行中、结果待校验、成功、失败/转人工等状态如何流转；没有状态就难以重试、审计和避免重复执行。
- **工具边界**：查询类、检索类、生成类和执行类职责不同；高风险执行不能由模型自由调用，必须经过权限、二次确认和审计。
- **异常路径**：参数缺失、无结果、冲突结果、低置信度、工具超时、工具失败分别怎么处理；不能只说“报错了就兜底”。
- **验证方式**：分别看任务完成率、工具成功率、引用/事实正确性、人工接管率、时延和成本；再用 Trace 和 Bad Case 定位首错节点。

### 口述成文要求

技术架构回答可以使用这样的自然衔接： “任务进来以后，我先……，因为这一步要判断……；确认后系统会调用……，它接收……并返回……；拿到结果以后，不是马上回复，而是先判断……；如果……就……，否则……；最后把……回写到……，这样后续能……。” 每一段都要保留“输入、处理、输出、判断、下一步”中的必要信息。

如果当前资料只有组件名称而没有真实调用顺序、参数、状态或返回值，不能把通用架构补成项目事实；直接回答版要明确“当前资料只确认到组件职责，具体调用顺序需要本人确认”，并在待补证据中列出缺口。

## 场景化口述规则

每个项目题、技术题、方案题、指标题和 Bad Case 题，先在开头或第一段尽快交代一个能让人看见问题的场景：**谁在什么时刻要完成什么任务，手上有什么信息，原流程卡在哪里或会产生什么损失**。场景不是额外的背景铺垫，而是后面“为什么要这样设计”的依据。

### 场景来源与事实边界

- **项目题只能使用资料中的真实场景**：用户角色、真实任务、已有流程、数据来源和已确认的痛点必须来自当前项目资料；不把另一个项目、行业常识或演示案例说成当时发生过。
- **通用题使用假设场景**：可以用“例如一个企业知识库客服场景”“假设用户正在比较两类方案”帮助解释，但要使用“例如、假设、可以”表达，不能把假设场景说成个人经历或项目事实。
- 资料没有具体场景时，先说清任务与输入输出，不虚构用户姓名、公司、数字或客户故事；将具体场景标为待补证据。

### 不同问题怎样带入场景

- **项目介绍**：从目标用户的一次真实任务切入，再带出旧流程、业务损失、项目目标和全链路。
- **技术架构/Agent/RAG/Workflow**：从一次任务请求切入，说明为什么此时要检索、调用工具或动态判断，而不是先定义技术名词。
- **产品方案/MVP**：从用户完成任务时的阻塞点切入，说明优先解决哪个最小闭环、哪些需求明确不做。
- **指标/评测**：先说哪类用户任务或风险需要被衡量，再解释指标口径、评测样本和阈值，避免孤立报数。
- **Bad Case/复盘**：从一个具体输入、预期和实际错误切入，沿着首错节点讲根因、改动和复测。
- **个人贡献/协作**：从本人在某个决策或交付节点遇到的真实问题切入，再讲判断、产物和协作边界。

### 成文检查

默认组织为：**场景 → 问题 → 判断 → 做法 → 结果或边界**。场景只保留能支撑当前问题的 1—2 句，不能为了故事感拉长，也不能把它单独标成“背景”。如果面试官已经给出明确场景，直接承接对方的场景，不重复重新设定。

## AI 技术表达层（产品经理口径）

所有项目题和 AI 技术题，不能只讲业务流程，也不能堆技术名词。至少补充一层“技术机制如何支撑产品结果”，并用产品经理能理解的方式解释：

- **大模型/LLM**：说明它负责理解、分类、生成还是规划，不把“用了大模型”当成完整方案。
- **Prompt**：说明任务目标、上下文、输出格式、约束和版本迭代，不只说“优化了 Prompt”。
- **RAG**：说明知识从哪里来、如何清洗切片、如何召回和重排、怎样返回来源，以及证据不足时怎么办。
- **Agent**：说明为什么需要动态判断、它接收什么输入、调用什么 Tool/Skill、输出什么结果、如何失败降级。
- **Skill/Tool**：说明确定性能力、参数、权限、返回结果和审计记录，避免把所有功能都说成 Agent。
- **Workflow**：说明触发条件、状态、分支、重试、人工确认和结果回写。
- **评测与护栏**：说明评测集、质量指标、业务指标、风险指标、成本/时延和人工兜底。

每次解释技术时遵循“它解决什么业务问题 → 在链路中怎么工作 → 产品上如何控制 → 用什么指标验证”。技术深度以产品经理能够和算法、研发对齐方案为标准，不扩展到没有资料支撑的底层实现或代码细节。

## 面试题库编排规则

整理面试题时，不按问题出现顺序平铺。先按资料来源和目标公司分组，再按考察能力归类，最后把具体问题放在对应大问题下面：

- **一级：目标公司或岗位**，例如公司 A、公司 B。
- **二级：考察模块**，例如岗位匹配、产品全生命周期、用户与市场、AI 技术架构、评测与商业化、协作与个人能力。
- **三级：具体问题**，例如“如何定义 MVP”“什么时候使用 Agent”“如何建立评测集”。
- **问题下：**放可直接口述回答、可能追问、资料依据和待补证据。

同义问题合并到同一个大问题下，不重复生成；一个问题同时适用于 GEO 和获客时，保留同一问题标题，但必须分别生成两份项目答案。新增题目优先检查是否已有同类模块，避免继续新增孤立问题。

## 逐字稿生成流程

1. **识别问题意图**：判断是项目介绍、背景、挑战、方案、架构、RAG、Agent、指标、评测、Bad Case、结果、个人贡献还是复盘。
2. **锁定项目范围**：读取问题中的项目名、当前项目上下文和资料的一级项目标题；范围不确定时停止拼接，先说明需要确认。
3. **检索证据**：优先取逐字稿中的已确认表述，再用同项目知识库补足业务、产品和技术细节；排除 Skill 本身、其他项目和无来源示例。
4. **组织口语答案**：先按总—分—总确定主线，再从产品全生命周期中选取相关维度，组织为“结论 → 用户/业务场景 → 我的做法 → 证据/结果 → 局限与下一步”，不先堆 Agent、RAG 等名词。
5. **检查事实边界**：逐句检查项目、来源、个人职责、数字、结果和完成状态；不确定内容移到待补证据。
6. **准备追问**：只生成与当前回答直接相关的 2—4 个追问，并指出每个追问需要补哪类证据。

## 不同问题的口述重点

| 问题类型 | 逐字稿必须回答 |
| --- | --- |
| 项目介绍 | 服务谁、解决什么问题、我负责什么、方案怎么落地、结果/当前状态 |
| 为什么做 | 用户场景、旧流程、损失或风险、为什么需要 AI |
| 产品方案 | 用户输入、系统判断、核心功能、人工/异常路径、为什么这样取舍 |
| Agent/RAG/Skill | 业务任务、组件职责、输入输出、触发条件、失败兜底、成本/时延/准确性取舍 |
| 指标/效果 | 指标定义、分子分母、数据来源、时间范围、线上/离线边界，不能只报数字 |
| Bad Case | 具体输入、错误输出、影响、首错节点、根因、改动、复测和残余风险 |
| 个人贡献 | 我主导的判断、产物、协作对象、没有负责的部分和可展示证据 |
| 复盘 | 当时限制、没有采用的方案、下一步验证和可迁移的方法 |

## 口述回答的成文规则

“直接回答版”必须是**一段连续的话**，直接回答面试官的问题；不得分段，不得把回答拆成“结论、背景与问题、具体做法、结果、复盘”五段，也不得使用这些词作为口述小标题。背景、用户、目标、产品方案、AI 技术机制、测试评测、Badcase、结果和个人职责，要通过“因为、所以、在这个过程中、为了验证、后来、我主要负责”等自然连接词融入同一段话。

以“你这个项目是怎么做的”为例，回答应先用一句话概括项目和业务问题，再连续说明服务用户、核心链路、AI 架构和关键取舍，接着说明测试评测、Badcase 或迭代，最后收束到项目结果、当前边界和本人职责；这些内容都写在同一个自然段里，而不是输出项目讲解提纲。只有“资料依据”“可能追问”“待补证据”等准备信息可以在口述稿之后另起结构。

## 追问处理

- 面试官追问“这个数字怎么算”时，补定义、分子分母、数据来源和时间范围。
- 追问“为什么这么设计”时，补用户任务、备选方案、成本、时延、准确性和风险取舍。
- 追问“具体怎么做”时，补输入、处理链路、输出、失败路径和个人负责的产物。
- 追问“举个例子”时，只从当前项目来源中找真实案例；没有案例就明确写待补证据。
- 连续追问仍围绕同一项目和同一证据缺口，不因为问题换一种说法就切换项目。

## 固定输出格式

```markdown
## 面试逐字稿

### 直接回答版（可直接照读）
[默认完整首答；自然口语；讲透当前问题所需的关键层；只放已确认事实和明确标注的证据状态]

### 如果需要更短
[仅在面试官明确要求简短回答时生成；保留结论、核心做法和结果/边界]

## 资料依据
- 当前项目：
- 使用来源：逐字稿 / 知识库 / 候选人背景
- 已确认事实：
- POC / 离线评测：
- 方案或目标：

## 可能追问
1. [追问]——需要补：[证据类型]
2. [追问]——需要补：[证据类型]

## 待补证据
- [没有资料支持的数字、职责、结果或完成状态]
```

“面试逐字稿”部分必须是候选人可以直接说出口的内容；资料依据、可能追问和待补证据是准备信息，不能混入口述稿。

## 表达要求

- 口语化但不随意，避免“首先、其次、综上所述”式论文表达。
- 每个回答至少包含一个具体用户场景或输入输出，不用“提升体验、实现智能化、构建多 Agent”等空话代替事实。
- 结果没有数字时，改说验证方式、当前阶段或业务观察，不自行补数字。
- 个人经历题才使用“我当时、我负责、我推动”；通用题使用“我会、建议、可以”。
- 不为了显得完整而硬塞个人背景、其他项目或未完成方案。
