# AI 产品术语表维护 Skill

## 目标

维护 `AI产品经理术语表.md`，让系统能通过术语和别名稳定检索通用 AI 产品知识，并生成可直接用于面试的通用方法论回答。术语表是通用资料，不是候选人项目经历库。

## 适用范围

在新增、合并、拆分、改写术语条目，补充同义词，或处理“扣子是什么”“RAG 怎么实现”“什么时候用 Agent”等通用问题时使用本 Skill。

- 项目经历、项目数据、个人职责、项目 Badcase：使用项目知识库和“AI 产品经理面试完整口述回答 Skill”。
- 面试回答的组织方式：使用“AI 产品经理面试完整口述回答 Skill”。
- 术语表只提供概念、选型原则、实现链路、边界与通用口述方法，不替代项目事实。

## 资料与事实边界

- 通用资料统一使用“可以 / 建议 / 我会”的表达；不得写成候选人的亲身项目经历，不得使用“我做过 / 我负责过 / 我们上线后”等表述。
- 未经来源确认的产品能力、版本差异、价格、合规要求或近期事实，不写成确定结论；标注待核实，或只写稳定的通用原理。
- 不把其他候选人的复盘、行业案例、示例指标或项目数据搬进术语表当作本人事实。
- 高风险场景优先写权威来源、规则/模型/人工分工、置信度、拒答、人工接管与审计，不用“模型会判断”代替控制方案。

## 术语条目标准结构

每个一级概念使用 `## 概念名`，紧接一行 `别名：别名 1、别名 2`。别名用于检索和语音纠错，必须是用户真实会说的词。

每个核心概念至少按以下顺序整理：

1. **一句话定义**：说明它是什么，不堆术语。
2. **解决什么业务问题**：说明用户、业务或交付上的价值。
3. **核心组成或实现链路**：说明关键组件、输入输出和控制点；链路用箭头表达。
4. **适用场景**：说明什么任务、数据条件、风险等级或组织条件下适合用。
5. **不适用场景或局限**：说明成本、时延、准确性、可控性、数据依赖或维护负担。
6. **1 分钟口述回答**：生成自然的通用方法论口述稿；信息完整，至少讲清定义、价值、机制和边界。若面试官未要求简短，不在 1 分钟处强行截断。
7. **区别和关系**：说明与 RAG、Workflow、Agent、Tool、Skill 等相邻概念的职责边界和协作关系。

简单、稳定的辅助术语可以使用精简版，但仍必须保留“定义、业务作用、边界/关联概念”三项，且不能与核心概念矛盾。

## 别名与检索规则

- 一个概念只保留一个 `##` 主标题；同义词全部放在 `别名：` 行，避免为同一概念建立多个相互冲突的正文条目。
- 优先收录中文全称、常见简称、英文写法、语音识别易错写法和业务口语；例如 Coze 的“扣子、字节扣子、Coze 平台”。
- 别名必须指向唯一主概念。歧义词不要直接绑定；必要时在条目中说明判别上下文。
- 新增或修改别名后，同步检查 `src/glossary.js` 的默认词表、语音纠错和相关测试；Markdown 的 `##` 标题与 `别名：` 行是解析器可读取的正式结构。
- 不把相近但不同的概念硬当同义词：例如 RAG 不等于向量数据库，Agent 不等于 Workflow，Skill 不等于 Tool。

## 必备概念与维护重点

### Coze / 扣子

- 覆盖 Coze / 扣子是什么、从零搭建应用的基本流程及适用边界。
- 讲清 Bot、Workflow、Plugin、Knowledge、Memory 的关系：Bot 是面向用户的应用入口；Workflow 编排稳定步骤；Plugin/Tool 连接外部能力；Knowledge 提供可检索资料；Memory 保存必要的会话或用户上下文。
- 写清何时适合快速验证、内部工具或标准化助手；何时因复杂权限、深度定制、强交易一致性或高度可控性而建议转向自研或专用系统。

### RAG

- 区分离线建库与在线检索：离线侧包含采集、清洗、切片、Metadata、索引、权限与版本；在线侧包含问题理解、混合召回、Rerank、上下文组装、生成、引用和日志。
- 说明 Chunking、Metadata、向量检索、关键词/BM25、混合召回、Rerank、引用与评测各自解决的问题。
- 说明 RAG 适合知识频繁变化、需要引用或有大量非结构化资料的任务；不适合纯确定性计算、必须实时查交易状态、缺少可靠知识源或答案必须零容错的任务。

### Agent、Workflow、Tool、Skill

- 清楚区分职责：Workflow 是预定义、可审计的流程；Agent 是根据中间结果动态判断和规划的执行者；Tool 是可调用的确定性外部能力；Skill 是任务规则、步骤、模板和工具使用规范的可复用能力包。
- 选型先问任务是否可预定义：稳定、规则清晰、需要强可控时建议 Workflow；步骤和工具选择随上下文变化时可以使用 Agent；关键写操作必须经权限、确认、日志和人工兜底。
- 写清协作链路，例如 Agent 可以选择 Tool 或触发 Workflow，Skill 可以约束 Agent 的任务方法；RAG 为其中需要外部知识的节点提供证据，不承担交易执行。

### AI 产品评测

- 覆盖数据集、场景和样本分布、Rubric、标注质检、Badcase、Trace、回归集，以及离线与线上指标的边界。
- 区分：离线评测验证能力和版本回归；线上指标验证真实使用与业务价值。不能用离线高分直接等同于线上效果。
- 说明评测闭环：目标 → 评测集 → Rubric/标注 → Trace 与归因 → 修复 → 回归集 → 灰度/线上监控。

### 高风险场景

- 对医疗、金融、法律、对外发布、隐私、交易和权限操作等场景，写清权威数据源、硬规则、模型判断、人工复核各自负责什么。
- 写清置信度阈值、证据不足时的拒答/澄清、越权或异常时的拦截、人工接管、完整审计与可回溯记录。
- 明确模型输出只能作为建议或辅助判断时，不能写成自动决策。

## 编写与改写流程

1. 判断请求是通用术语维护还是项目经历整理；只有前者进入本 Skill。
2. 确定主概念、范围和别名；先查是否已有同义条目，避免重复建词。
3. 用“定义 → 业务问题 → 链路 → 适用 → 局限 → 口述 → 关系”补齐核心概念。
4. 对容易混淆的概念，明确给出选型判断和分工，不只给定义。
5. 检查通用表达、事实来源、别名冲突与 Markdown 解析结构。
6. 修改后用典型问法验证检索：主标题、每个高频别名、相邻概念对比问法，以及高风险边界问法。

## 输出质量闸门

提交前逐项确认：

- 主标题、别名和正文概念是否一致，且别名无冲突？
- 是否把概念的业务价值、实现链路和选型边界都讲清了？
- 是否区分了 RAG、Agent、Workflow、Tool、Skill 的职责？
- 是否包含可直接口述的通用回答，却没有伪造成个人项目经历？
- 是否对评测、高风险和时效性信息保留了必要的边界与待核实状态？
- 修改是否保持 `## 标题` 和 `别名：` 的解析兼容性，并同步必要的词表/测试？
