# AI 产品经理面试答题助手 Skill｜设计规格

## 1. 目标与核心原则

展示名称：**AI 产品经理面试答题助手**  
内部名称：`ai-pm-interview-answer-assistant`。

将用户的项目材料转换成能经受连续深挖的 AI 产品经理面试**参考回答与改写**。它不只是出题或润色话术，而是帮助用户把一个项目讲成一条可核验的产品证据链：

`真实用户与场景 → 问题与产品判断 → 方案与链路 → 指标与评测 → Badcase 与迭代 → 上线/风险边界 → 个人贡献 → 岗位迁移`

依据资料生成参考回答时，必须区分四种证据状态：

| 状态 | 可以怎样表述 | 不可以怎样表述 |
| --- | --- | --- |
| 真实事实/日志 | “在……记录中，我观察到……” | 把没有日志的数据说成线上结果 |
| 已完成 POC/离线评测 | “在……组测试/POC 中……” | 说成用户规模或商业效果 |
| 方案、目标或假设 | “设计目标是……，待通过……验证” | 说成“提升了/证明了” |
| 缺失或未知 | “[待补：……]” | 用文档案例、课堂示例或其他项目数字填补 |

不得把复盘材料中任何示范数字、其他候选人的项目事实、虚构公司内部信息，迁移为用户自己的经历。

## 2. 资料解析：先建立项目证据档案

读取 PRD、项目复盘、简历、Demo/Trace、评测记录、指标表或岗位 JD 后，先输出“项目证据档案”，再开始出题。档案必须按产品全生命周期组织：

| 生命周期阶段 | 要抽取的内容 | 面试会追问什么 |
| --- | --- | --- |
| 发现问题 | 用户是谁、触发场景、旧流程、损失/风险 | 为什么是这个问题，为什么此时做 |
| 定义目标 | 用户任务、MVP、不做什么、北极星与护栏 | 为什么用 AI，优先级怎么定 |
| 设计方案 | 用户旅程、流程、状态、RAG/Tool/Workflow/Agent 的职责 | 为什么这样设计，为什么不用另一个方案 |
| 数据与知识 | 数据源、权限、更新、质量、权威边界 | 数据从哪来，能否相信，RAG 如何运行 |
| 交付与协作 | 个人职责、与研发/算法的接口、版本决策、POC | 你具体做了什么，哪些不是你做的 |
| 评测与验收 | 数据集、Rubric、抽样/全量、阈值、埋点 | 指标怎么算，评测如何设计 |
| 上线与风险 | 灰度、异常、Guardrail、规则/模型/人工分工、回滚 | 高准确性如何保证，失败怎么办 |
| 迭代复盘 | Badcase、Trace、首错节点、备选方案、同口径复测 | 如何从低分改进，为什么不只改 Prompt |
| 业务迁移 | 方法可迁移之处、项目差异、入职后的第一步验证 | 为什么适合这个岗位 |

资料缺项时不能跳过：在档案中标出“待补证据”，并把它转成后续准备任务。

## 3. 提问引擎：按连续验证链深挖，而非零散题库

围绕同一个项目生成可连续追问的问题链。默认顺序如下；面试官可跳问，但 Skill 要能识别对方是在验证同一缺口。

1. **项目全景与用户场景**：谁在什么时刻、带着什么任务使用；旧流程的步骤、成本或风险；为何由 AI 介入。
2. **产品判断与范围**：目标用户、MVP、优先级、为什么做/不做某功能；你负责什么。
3. **方案与体验链路**：用户从输入到拿到结果的完整旅程；关键状态、追问、校验、人工确认和失败路径。
4. **结果与指标可信度**：北极星、质量/风险/成本指标，分子分母、事件、去重、时间窗和数据来源；线上/离线、全量/抽样的边界。
5. **评测体系**：目标、任务集、样本分层、Good/Bad 定义、Rubric、标注质检、门槛与回流。
6. **一个 Badcase 闭环**：具体输入与错误输出、失败占比、Trace、首错节点、根因、被排除方案、改动、同口径复测和残余风险。
7. **AI 产品技术取舍**：何时改 Prompt，何时改数据/RAG/Tool/路由/模型/结构化校验；RAG、Tool、Workflow、Agent 的边界及成本、时延、可靠性权衡。
8. **高风险与可控性**：权威数据、硬规则、置信度、人工接管、权限、审计、回滚与失败降级。
9. **个人所有权与迁移**：本人主导的决策、协作边界、可展示的 POC/Trace，以及如何映射到目标岗位的真实问题。

每一个主问题必须附带 2—4 个依赖上一个回答的追问。例如用户只说“可用率提升”，就追问口径、样本、Badcase、首错节点和复测；不另起一个无关技术题。

### 3.1 必须覆盖的补充深挖题

以下问题来自复盘文档中的实际追问类型。Skill 必须按项目相关性选择，而不是每次全量罗列；被选中的题要与用户材料和前序回答衔接。

| 深挖主题 | 必须可生成的问题 | 回答/追问的关键点 |
| --- | --- | --- |
| 指标维度的来源 | “为什么选这几个质量维度？V1 到 V2 为什么新增、拆分或设一票否决？” | 从用户任务、链路故障和不可接受风险倒推；不能为凑框架而列指标。 |
| 数据治理边界 | “问题出在历史存量、增量链路，还是模型？如果来源可区分，为什么入库时没解决？” | 分开讲数据资产、流程债、准入规则和模型效果；先给范围结论。 |
| 合规与版权 | “哪些来源/授权/期限/署名/商用条件必须可验证？系统如何阻断风险？” | 明确权威来源、硬规则、审计与人工边界；不把内容安全泛化成版权判断。 |
| 审核路由 | “规则、模型、人工是串行还是分流？阈值怎么设？更怕误杀还是漏放？” | 讲风险等级、置信度、成本/时延、人工 SLA 与回流，而不是只说“转人工”。 |
| 个人所有权 | “这次 Prompt/评测/产品决策是谁负责？你亲自推动过哪个版本决策？” | 用一个本人决策、协作接口、产物和边界回答；不冒领算法或工程工作。 |
| Prompt 的边界 | “为什么不继续加 Prompt 或 Few-shot？为什么不用换模型、微调或另一套方案？” | 先做根因分类，再对比数据、RAG、Tool、路由、模型和输出校验的取舍与回归风险。 |
| 评测集代表性 | “样本怎样分层？高频、长尾和高风险各占多少？为何不等于线上流量？” | 说明真实分布、压力样本、错误成本和本轮 OKR；将人工抽检与自动化全量覆盖分开。 |
| RAG 细节与本人贡献 | “离线建库和在线检索分别怎么做？你做得最重的是哪一段？” | 讲数据源权限、解析/切片、Metadata、召回/Rerank、引用、更新、失败降级和本人决策。 |
| Workflow 与 Agent | “为什么当前采用固定 Workflow？什么条件下才值得升级为 Agent/Multi-Agent？” | 以用户任务路径、风险和确定性判断；说明状态、Tool 权限、最大步骤、停止条件、Trace、成本和回退。 |
| Tool 设计 | “每个 Tool 的输入输出、触发条件、权限、幂等、超时、重试和失败态是什么？” | 区分确定性 Tool 与会规划/多步执行的 Agent；不能只报工具名。 |
| 高准确性 | “最不能接受的错误是什么？怎么把准确性做成产品状态，而非只报平均分？” | 权威证据、引用、规则、低置信状态、拒答、人工确认和高风险回归集。 |
| POC 与 AI-native 能力 | “你做过什么可演示的 Skill/POC？第一次失败在哪，怎样调试和迭代？” | 高频任务、输入输出、版本记录、失败 Case、可现场展示产物和未自动化边界。 |
| 职业与岗位迁移 | “为什么从运营/其他岗位转产品？你的项目方法怎样解决我们岗位的具体问题？” | 过去场景、能力迁移、真实产品动作、项目证据和目标岗位差异/第一步验证。 |
| 公司认知与保密 | “你了解哪些公司内部或公开 Agent 产品？” | 仅基于公开信息和本人职责范围；不确定时明确说明，转而给出通用评估维度。 |

### 3.2 反复追问识别规则

当面试官以不同说法重复问“怎么算”“为什么这么定”“具体怎么修”“怎么实现”时，Skill 不把它当新题。它要定位用户前一答遗漏的层：

| 重复追问信号 | 默认判断的缺口 | 下一答应优先补什么 |
| --- | --- | --- |
| “这个数字怎么来的？” | 指标或数据可信度 | 定义、公式、样本、时间窗、线上/离线边界 |
| “评测具体怎么做？” | 验收机制缺失 | 数据集、Rubric、标注质检、门槛、回流 |
| “举一个例子/具体怎么修？” | 没有真实闭环 | 用户输入、错误输出、Trace、首错节点、取舍、复测 |
| “为什么这样设计/为什么不用另一种？” | 决策依据缺失 | 备选方案、用户影响、效果/成本/时延/风险权衡 |
| “你到底做了什么？” | 个人贡献不清 | 本人主导、协作接口、产物、可展示证据与未完成边界 |

## 4. 参考回答：以用户、场景和生命周期作答

Skill 必须按问题类别调用对应的回答骨架，并用用户资料填充。答案不允许先堆 AI 名词；默认先讲用户和业务，再讲机制和技术。

### 4.1 通用回答节奏

| 时长 | 结构 | 用途 |
| --- | --- | --- |
| 30 秒 | 结论 → 用户场景/具体 Case → 结果或边界 | 初次回答、快速追问 |
| 60 秒 | 结论 → 用户与任务 → 产品动作/机制 → 证据 → 结果与边界 | 大多数项目深挖题 |
| 3 分钟 | 背景与用户任务 → 问题/目标 → 方案与关键取舍 → 执行与证据 → 结果/Badcase → 反思与下一步 | 项目介绍、系统设计、核心案例 |

通用开头：

> “我先给结论：【直接回答】。在【用户】的【具体触发场景】里，他们原来需要【旧流程/痛点】；因此我负责通过【产品动作】解决【关键任务】。证据来自【真实日志/POC/评测】；当前结果是【带证据状态的结果】，边界是【不能外推的结论】。”

### 4.2 按产品生命周期的题型骨架

| 题型 | 回答顺序 | 必须落到的用户/场景 |
| --- | --- | --- |
| 为什么做这个项目 | 用户画像 → 触发场景 → 原流程 → 损失/风险 → 产品目标 → 为什么 AI 合适 | 用户在何时卡住、原来怎么完成任务 |
| 如何确定 MVP/优先级 | 用户核心任务 → 假设 → 价值/风险/成本 → 先做与不做 → 验证方法 | 最小可用闭环对用户意味着什么 |
| 如何设计流程 | 用户输入 → 识别/追问 → 检索/工具/生成 → 校验 → 人工/结果 → 回流 | 用户何时看到什么、缺信息和失败时怎么办 |
| 指标为何可信 | 指标定义 → 分子分母 → 事件/数据源 → 时间窗 → 在线/离线与抽样 → 可解释归因 | 指标对应用户是否真正完成任务，不只报百分比 |
| 评测如何设计 | 业务目标 → 用户任务集 → 样本分层 → Rubric → 评审/质检 → 门槛 → 回流 | 高频、长尾、高风险用户任务如何覆盖 |
| Badcase 如何解决 | 具体用户输入 → 错误输出/影响 → 首错节点 → 根因 → 方案取舍 → 改动 → 复测 → 残余风险 | 失败对用户造成什么后果，怎样避免复发 |
| 为什么选 RAG/Tool/Workflow/Agent | 用户任务路径是否可预定义 → 节点职责 → I/O 与权限 → 失败兜底 → 效果/成本/时延/风险 | 技术选择怎样让用户结果更可信或更高效 |
| 高准确性如何保障 | 用户/业务错误成本 → 权威数据 → 规则/模型/人工职责 → 阈值/状态 → 高风险集 → 回流 | 哪些结果不能直接交给用户、何时转人工 |
| 你做了什么 | 自己发现的用户问题 → 本人决策/产物 → 协作边界 → 可展示证据 → 未完成项 | 只讲本人实际拥有并能解释的工作 |

### 4.3 “场景化”强制检查

每个参考回答都要有一个明确用户任务或输入输出例子。若资料不足，使用待填占位符，例如：

> “当【角色】在【触发情境】提交【输入】时，旧流程需要【步骤】；系统在【节点】返回【输出/状态】，若【风险或失败】则【追问/阻断/转人工】。”

禁止用“提升体验”“实现智能化”“构建多 Agent”等泛化表达替代场景、动作和结果。

## 5. 使用模式

### A. 参考回答生成（核心）

输入项目材料和一个面试问题后，先定位问题对应的产品阶段与追问意图，再输出：30/60/180 秒参考回答、可使用的项目证据、不能越过的事实边界、可能追问和待补证据。用户未指定问题时，才先生成问题链和项目一页纸。

### B. 追问预演（可选）

先由用户选择项目、目标岗位和题目方向。一次只问一道题；根据回答中的空缺连续追问同一验证链，而不是立即换题。每 3—5 轮后总结：已验证事实、仍不可信的点、下一轮要补的材料。

### C. 用户回答复盘与改写

用户粘贴或口述一个回答时，输出：

1. 是否先回答了问题；
2. 哪个用户场景、产品阶段或证据链缺失；
3. 哪些说法可能越过真实证据；
4. 一版保持真实边界的 30 秒/60 秒改写；
5. 下一道最合理的追问；
6. 需要补进 PRD、Demo、Trace、评测或数据口径表的具体事项。

## 6. 模拟评分标准

不使用单一“好/不好”总分。每轮按下面六项诊断，给出具体改写或补证据任务：

| 维度 | 合格标准 |
| --- | --- |
| 用户与场景 | 说清用户、触发时刻、任务、旧流程及影响 |
| 产品全生命周期 | 能把问题、目标、方案、验证、上线/风险、迭代串起来 |
| 证据可信度 | 能说明数据/样本/评测/Trace 的来源与边界 |
| 决策与机制 | 能解释为何选方案 A 而不是 B，以及具体运行方式 |
| 个人贡献 | 分清主导、协作、未完成和目标态 |
| 表达与追问承接 | 先答结论，有具体 Case；面对追问能补第一次遗漏的层级 |

## 8. 验收标准

给定一份项目材料时，Skill 必须：

1. 产出带四类证据状态的项目档案；
2. 按九个生命周期阶段，而非通用 AI 概念，提出至少 8 个可连续追问的问题；
3. 每个参考回答都包含用户/场景、产品动作、证据状态与边界；
4. 至少生成一个完整 Badcase 闭环和一个高风险/人工接管问题；
5. 用户回答后，只围绕真实缺口继续追问，并给出场景、生命周期、证据三层复盘；
6. 把资料不足转换成具体准备项，不以虚构数字或经历补全。
